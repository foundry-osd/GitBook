# Windows PE bootstrap

The bootstrap prepares the Windows PE session, starts Foundry Connect, and launches Foundry Deploy after Connect succeeds. Use this page when startup stops before the deployment wizard appears.

## Current boot media

The flow below is verified against Foundry [v26.9.9.1](https://github.com/foundry-osd/foundry/releases/tag/v26.9.9.1). Media generated by this release starts the PowerShell bootstrap, `FoundryBootstrap.ps1`.

The console shows these sections in order:

| Console section | What happens |
| --- | --- |
| Runtime | Selects the x64 or ARM64 runtime and storage location. A volume labelled **Foundry Cache** takes precedence; otherwise temporary Windows PE storage is used. |
| Network services | Attempts to start wired authentication and supported wireless services. |
| Foundry.Connect | Resolves the application, starts it, and waits for the network workflow to finish. |
| System preparation | Attempts to correct the clock and configure the time zone after Connect succeeds. |
| Runtime cache | Checks for a Connect runtime update on release-provisioned USB media. This check is skipped for ISO mode and debug-provisioned Connect. |
| Foundry.Deploy | Resolves the deployment application and launches its process. |
| Completed | Confirms that the bootstrap has finished launching Deploy. |

**Completed does not confirm that the Deploy wizard is ready or that Windows deployment succeeded.** The current bootstrap does not wait for Deploy to finish initializing. If the wizard does not appear, collect both Bootstrap and Deploy logs.

Closing or cancelling Foundry Connect stops the boot workflow; it does not bypass network readiness. A Connect startup or configuration failure also prevents Deploy from launching. See [Network readiness](../foundry-connect/network-readiness.md) for the technician workflow.

## Cache and connectivity

The bootstrap tries to use an available Connect runtime before requiring a release lookup, so Connect can help establish networking. Application release lookup or download failures can fall back to usable cached content or an embedded archive when one is available. A fallback warning can therefore be followed by a successful launch.

A cache does not guarantee a fully offline deployment. Connect still requires its connectivity checks to succeed, and the selected Windows, drivers, catalogs, or Autopilot workflow may require additional services. If neither usable local content nor a downloadable runtime is available, boot stops before the affected application launches.

Debug-provisioned runtimes skip the normal release update lookup. Record whether the media uses release or debug content when reporting a startup problem.

## Collect startup evidence

Record the last console section, the displayed result, and the diagnostic session ID. Bootstrap, Connect, and Deploy share that ID so their log entries can be matched across the same boot.

Start with `FoundryBootstrap.log`, then collect the affected application's log. See [Windows PE log location](../troubleshooting/logs-and-support.md#windows-pe-log-location) for filenames, cache copies, and the information to preserve before rebooting.

## Unreleased .NET Bootstrap preview

{% hint style="info" %}
**Migration preview:** The first migration change introduces a standalone .NET 10 console application, `Foundry.Bootstrap`, for development and validation. It does not switch generated boot media away from the PowerShell bootstrap. No technician action or manual replacement on production media is required.
{% endhint %}

The preview follows the existing Connect-to-Deploy sequence and presents five stages: prepare environment, start Connect, prepare system, prepare deployment application, and start Deploy. Text statuses distinguish running work, completion, recoverable warnings, cancellation, and failure. The final result identifies whether Deploy was launched or why boot stopped; detailed diagnostics remain in the local logs.

Bootstrap-specific PostHog reporting, persistent remote-diagnostic replay, and explicit Connect/Deploy readiness acknowledgements are planned follow-up work. They are not part of this first migration change. Existing application telemetry remains governed by [Telemetry and privacy](telemetry-and-privacy.md).

Release packaging and automatic inclusion in newly generated media will follow separately. Updating Foundry OSD alone does not replace the bootstrap on previously distributed media; see [Application and boot media updates](supported-versions.md#application-and-boot-media-updates).
